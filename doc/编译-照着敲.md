## 二、先确认离线包已正确解压

假设你把所有文件放在 `D:\IQmol`，源码目录是 `D:\IQmol\IQmol-src`。

### 2.1 四包解压顺序（顺序错了会白干）

| 包 | 包顶层结构 | 解压位置 |
|---|---|---|
| `IQmol-submodules.tar.gz` | `modules/` | `D:\IQmol\IQmol-src\`（源码根） |
| `IQmol-openbabel-deps.tar.gz` | `external/` | `D:\IQmol\IQmol-src\modules\openbabel\` |
| `IQmol-openbabel-fix.tar.gz` | `modules/openbabel/` | `D:\IQmol\IQmol-src\`（**源码根**） |
| `IQmol-openbabel-formats-fix.tar.gz` | `modules/openbabel/` | `D:\IQmol\IQmol-src\`（**源码根**） |

> **警告**：fix / formats 两包顶层是 `modules/openbabel/`，所以解压位置是**源码根**。
> 若在 `modules\openbabel\` 目录里解压，会落成嵌套的
> `modules\openbabel\modules\openbabel\...`，补丁完全不生效（本项目已实际踩过）。
> 另外：重新解压 submodules 完整包会把 openbabel 的修复版 CMakeLists.txt 覆盖回
> 未修版——`build_windows.sh` 会自动检测并修复，无需手动处理。

**必须用 MINGW64 终端的 tar 命令解压**（假设包都在 `/d/IQmol/`）：

```bash
cd /d/IQmol/IQmol-src
tar -xzf ../IQmol-submodules.tar.gz              # → modules/
tar -xzf ../IQmol-openbabel-deps.tar.gz -C modules/openbabel   # → external/
tar -xzf ../IQmol-openbabel-fix.tar.gz           # 在源码根解压！
tar -xzf ../IQmol-openbabel-formats-fix.tar.gz   # 在源码根解压！
```

> 不要用 360 压缩、7-Zip、WinRAR 的图形界面解压 `.tar.gz`，它们会**静默丢文件**（已反复验证）。

### 2.2 快速检查文件是否齐全

在 MINGW64 终端执行：

```bash
cd /d/IQmol/IQmol-src
# 检查子模块聚合脚本
ls -1 modules/CMakeLists.txt
# 检查 OpenBabel 关键格式源文件（如果缺失，说明解压不完整）
ls -1 modules/openbabel/src/formats/xml/pubchem.cpp
ls -1 modules/openbabel/src/formats/json/chemdoodlejsonformat.cpp
ls -1 modules/openbabel/src/formats/json/pubchemjsonformat.cpp
# 检查 external 依赖
ls -1 modules/openbabel/external/maeparser-v1.2.3/README.md
ls -1 modules/openbabel/external/coordgen-master/README.md
ls -1 modules/openbabel/external/rapidjson-1.1.0/readme.md
# 检查 libinchi 和 test（fix 包补充的内容）
ls -1 modules/openbabel/src/formats/libinchi/ichidrp.h
ls -1 modules/openbabel/test/CMakeLists.txt
```

上面 9 条命令都应该出现文件路径，**任何一条提示 "No such file or directory"，先回去检查包是否解压完整/顺序是否正确**。

## 三、推荐方式：一键脚本

```bash
cd /d/IQmol/IQmol-src
bash ./scripts/build_windows.sh
```

脚本会自动：

1. 补全缺失的 `modules/CMakeLists.txt`；
2. 检测并修复 `openbabel/CMakeLists.txt` 的 `uninstall` 目标冲突；
3. 检测 CMake 4.x 并自动下载 portable CMake 3.31 到 `.tools/`；
4. **配置指纹自检**：比对关键配置（`BUILD_SHARED` 同步、`--whole-archive`），
   发生变化自动重新 configure，避免「改了 CMakeLists 但构建没跟上」；
5. configure（首次大约 1~5 分钟）；
6. 编译（首次大约 20~60 分钟）。

### 3.1 脚本的增量行为

脚本默认**增量**：

- 如果 `build/` 里已有 `CMakeCache.txt` 且关键配置未变，再次运行会**跳过 configure 直接编译**；
- 编译中断了重跑，会继续编剩下的 `.o`，不会从头开始；
- 若检测到 `CMakeLists.txt` 的关键配置变化，会**自动重新 configure**（无需手删缓存）。

**除非你要换 CMake 参数，否则不要删 `build/`**。删一次就要重新 configure 一次，慢得没意义。

### 3.2 常用用法

| 命令 | 作用 |
|------|------|
| `bash ./scripts/build_windows.sh` | 增量编译（推荐日常用） |
| `bash ./scripts/build_windows.sh --clean` | 删掉 `build/` 从零 configure（慢） |
| `JOBS=8 bash ./scripts/build_windows.sh` | 强制用 8 线程编译 |
| `CMAKE_BIN="D:/cmake-3.31.6/bin/cmake.exe" bash ./scripts/build_windows.sh` | 指定已下载的 CMake 3.31 |

> 构建脚本位于 `scripts/` 下。若报 `No such file or directory`，说明该文件未同步，
> 重新从仓库拉取即可（参见《构建说明-中文版.md》）。

### 3.3 如果提示缺 `modules_CMakeLists.txt`

把交付的 `modules_CMakeLists.txt` 放到 `IQmol-src/scripts/` 同一目录，或脚本会从 GitHub 拉取。网络不稳时请手动放置。

## 四、手动命令方式（适合排查问题）

如果你不想用脚本，按下面顺序敲：

```bash
# 1. 进入源码目录
cd /d/IQmol/IQmol-src

# 2. 确认用 CMake 3.31.x，而不是 4.x
#    若系统是 CMake 4.x，到 .tools/ 里找脚本自动下载的 portable 版
cmake31="D:/IQmol/IQmol-src/.tools/cmake-3.31.6/bin/cmake.exe"
"$cmake31" --version   # 应显示 3.31.x

# 3. 新建/进入构建目录（如果已存在且有 CMakeCache.txt，直接进去 make）
mkdir -p build
cd build

# 4. 首次 configure（出现 -- Configuring done 才算完）
"$cmake31" .. \
  -G "MinGW Makefiles" \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH="/d/msys64/mingw64" \
  -DCMAKE_CXX_FLAGS="-fpermissive -std=gnu++17 -Wno-deprecated" \
  -DCMAKE_MAKE_PROGRAM="mingw32-make" \
  -DBOOST_ROOT="/d/msys64/mingw64" \
  2>&1 | tee config.log

# 5. 编译（并行度按你 CPU 核数，建议 4~8）
mingw32-make -j4 2>&1 | tee make.log
```

configure 成功后，`build/` 目录里会生成 `CMakeCache.txt`。以后只要不删这个目录，**直接进去 `mingw32-make -j4` 即可**，不要再重跑 `cmake ..`。

## 五、编译省时的三条铁律

1. **首次 configure 慢是正常的**（1~5 分钟），因为它要调用 MinGW 编译大量小程序做特性检测；后续只要保留 `build/`，就不会再花这个时间。
2. **不要习惯性 `rm -rf build/`**。这是用户最容易踩的坑：删一次就要重新 configure 一次。
3. **并行度 `-j4` 到 `-j8` 为宜**。开满（如 `-j32`）容易因单编译单元 1~2GB 峰值内存而 OOM，反而更慢。

## 六、编译成功后拿到什么

编译产物在 `D:\IQmol\IQmol-src\build\` 下：

- `build/bin/IQmol.exe`：主程序（**注意在 `bin/` 子目录里**）；
- `build/bin/translations/zh_CN.qm`：中文翻译文件（构建时由 CMake 调用 `lrelease` 自动生成）。

### 6.1 运行前必须做一次部署

Windows 版**不能直接双击运行**，需要先复制 Qt 插件、MinGW 运行库与资源。
仓库提供了专用脚本，一条命令搞定：

```bash
cd /d/IQmol/IQmol-src
bash ./scripts/deploy_windows.sh
```

脚本会依次处理：

| 步骤 | 内容 |
|------|------|
| 1 | `windeployqt` 复制 Qt DLL 与平台插件（缺失时回退为手工复制） |
| 2 | 同步 Qt 插件到 `build/lib/` 与 `build/lib/plugins/`（对齐源码的 `addLibraryPath`） |
| 3 | 复制 MinGW 运行库（`libstdc++-6.dll` 等） |
| 4 | 复制 IQmol 资源 `share/`（着色器、片段库等） |
| 5 | 复制 OpenBabel 数据到 `build/share/openbabel/`（扁平 + `3.1.1/` 版本子目录双份） |
| 6 | 确认 `bin/translations/zh_CN.qm` 就位（缺失则现场 `lrelease`） |
| 7 | 自检力场参数文件（`UFF.prm` / `ghemical.prm` / `gaff.prm` / `mm2.prm`） |

部署完成后启动：

```bash
cd /d/IQmol/IQmol-src/build/bin
./IQmol.exe
```

> **`--stage` 选项**：`bash ./scripts/deploy_windows.sh --stage D:\dist` 会把结果整理成
> `D:\dist\IQmol\{bin,share,lib}`，便于打包分发。

### 6.2 目录约定（为什么是这些路径）

IQmol 在 Windows 下按以下约定查找运行时文件（源码 `src/Main/IQmolApplication.C`）：

| 用途 | 路径 |
|------|------|
| 运行时根 | 可执行文件的**上一级**（`build/bin/IQmol.exe` → `build/`） |
| Qt 插件 | `<根>/lib`、`<根>/lib/plugins` |
| OpenBabel 数据 | `<根>/share/openbabel` |
| 着色器 / 片段库 | `<根>/share/shaders`、`<根>/share/fragments` |
| 中文翻译 | `<可执行文件同级>/translations/zh_CN.qm` |

`deploy_windows.sh` 正是按这套约定铺文件的，所以**跑完它才能正常启动**。

## 七、常见失败与排查

| 现象 | 原因 | 处理 |
|------|------|------|
| `cmake ... CMP0042 OLD` 报错 | 用了 CMake 4.x | 改用 `build_windows.sh` 自动下载的 3.31，或手动指定 portable CMake 3.31 |
| `bash: scripts/build_windows.sh: No such file or directory` | 本地 `scripts/` 缺该文件（仓库后续才加入的） | 见《构建说明-中文版.md》重新拉取脚本 |
| `undefined reference to __imp__ZN9QGLViewer...` / `__imp__ZN4YAML...` | QGLViewer / yaml-cpp 为静态库，但头文件按 DLL 导入展开 | 确认 `CMakeLists.txt` 含 `QGLVIEWER_STATIC YAML_CPP_STATIC_DEFINE`（已修） |
| `undefined reference to __imp_glStencil*` / `gluNewQuadric` 等 | OpenGL / GLU 未链接（CMake 3.14+ 不再设 `OPENGL_LIBRARIES`） | 确认 `CMakeLists.txt` 含 `OPENGL_TARGET` / `GLU_TARGET` 收敛（已修） |
| `No rule to make target 'modules/openbabel/src/libopenbabel.a'` | `--whole-archive` 误用 `$<TARGET_FILE:...>` 破坏依赖跟踪 | 确认用**目标名** `openbabel` 且有 `add_dependencies`（已修） |
| 运行报 `Unable to find OpenBabel plugins` | OpenBabel 子模块 `BUILD_SHARED` 未与顶层 `BUILD_SHARED_LIBS` 同步，插件未内联 | 确认 `CMakeLists.txt` 含 `set(BUILD_SHARED OFF CACHE ... FORCE)`（已修） |
| 运行报 `Failed to load force field: UFF` | 静态库中插件自注册对象被链接器丢弃 | 确认 `openbabel` 被 `--whole-archive` 包裹（已修） |
| `add_subdirectory given source "libinchi" not an existing directory` | fix 包没解压或顺序错了 | 重按顺序解压 `IQmol-openbabel-fix.tar.gz` |
| `ADD_CUSTOM_TARGET cannot create target "uninstall" ... already exists` | fix 包没覆盖到 openbabel/CMakeLists.txt | 同上，确认 fix 包覆盖了 `modules/openbabel/CMakeLists.txt` |
| `No SOURCES given to target: pubchem / xmlformat / ...` | formats 包没解压 / 解压丢文件 | 重按顺序解压 `IQmol-openbabel-formats-fix.tar.gz`，并检查 `src/formats/xml/`、`src/formats/json/` |
| `babelconfig.h: No such file or directory` | 根 CMakeLists 没打好补丁 | 确认源码是最新 `master`（补丁已在仓库里） |
| 改了 `CMakeLists.txt` 但行为没变 | 构建未重新 configure | 重跑脚本（脚本有配置指纹自检，会自动重配）；或确认脚本确实执行成功 |
| 编译成功但界面还是英文 | 缺少 `bin/translations/zh_CN.qm` | 见 6.1，跑 `deploy_windows.sh` |
| 编译一半报错，第二次直接跑又好了 | 大概率 MinGW 文件锁 / 并行问题 | 单线程重跑：`mingw32-make -j1` 或重跑脚本 |

> **排查心法**：很多报错的**提示文案本身是误导性的**。
> 例如 `Failed to load force field` 提示「BABEL_DATADIR 可能没设对」，
> 但实际原因通常是构建配置（见上表）。遇到含「环境变量/路径」提示的报错时，
> 先确认构建配置是否真的生效，再查运行环境。

## 八、如果还有问题

请把以下信息贴出来：

1. 你执行的**完整命令**；
2. configure 或编译输出中**第一条** `error:`（或 `CMake Error`）前后 10 行；
3. `build/CMakeCache.txt` 的前 20 行（确认 CMake 版本和生成器）。

若脚本报错，把 `build_run.log` 的**头部 + 关键行 + 尾部**贴出来：

```bash
bash ./scripts/build_windows.sh 2>&1 | tee build_run.log
head -30 build_run.log
grep -nE "ERROR|error:|CMake Error|Built target" build_run.log | tail -30
tail -40 build_run.log
```
