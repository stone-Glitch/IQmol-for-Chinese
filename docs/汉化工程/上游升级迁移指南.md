# 上游升级迁移指南

**目的**：上游 [`nutjunkie/IQmol3`](https://github.com/nutjunkie/IQmol3) 发布新版本后，
用最低成本把本仓库的汉化成果迁移过去。

---

## 一、基础事实（先理解，再动手）

| 项 | 事实 |
|---|---|
| 仓库关系 | 本仓库 **fork 自上游**，与上游**共享 git 历史** |
| 当前基线 | 上游提交 `af7ff60`（即我们与上游的 merge-base） |
| 我们的改动 | 相对基线 **+286 新增文件 / 132 个修改文件 / 0 删除**（2026-10-02 实测） |
| 改动性质 | 全部是**增量修改**（汉化 tr() 包裹、构建修复、新增文档资产） |
| 迁移原理 | 因为共享历史，可直接 `git merge` 吸收上游更新，冲突通常很少 |
| 高风险文件 | `CMakeLists.txt`（上游 224 行 / 本仓库 646 行，整体重写） |

> **为什么能"快速迁移"**：我们的每次改动都是叠加在上游代码之上的小增量，
> 而非重写。git 能自动分辨"哪些是上游改的、哪些是我们改的"。
>
> 唯一的例外是 `CMakeLists.txt` —— 这个文件是整体重写，属**高风险项**，
> 两条路线都需特别关注（见 §4.2）。

## 一点五、两条迁移路线（先选路线，再看流程）

本仓库提供**两条**上游迁移路线，按上游改动幅度二选一：

| 路线 | 工具 | 适用场景 | 实测效果 |
|---|---|---|---|
| **A. git 合并** | `scripts/sync_upstream.sh --merge` | 共享 git 历史、上游改动不大 | 冲突少时 10 分钟内完成 |
| **B. 干净树重放** | `scripts/migrate_to_upstream.sh --apply` | 上游大重构 / 想从零干净重建 | **95/95 文件 100% 复现**（源码 69 + 界面资源 22 + 构建层 4） |

### 路线 B：一条命令完成（推荐用于大版本升级）

```bash
# 1. 取一份干净的上游检出
git clone https://ghfast.top/https://github.com/nutjunkie/IQmol3.git /d/IQmol-upstream

# 2. 预检（不落盘）
bash <本仓库>/scripts/migrate_to_upstream.sh --check --target /d/IQmol-upstream

# 3. 实际执行六步迁移（推荐带 --selfcheck：迁移后自动比对）
bash <本仓库>/scripts/migrate_to_upstream.sh --apply --target /d/IQmol-upstream --selfcheck

# 3'. 已经迁移过、只想复核结果时
bash <本仓库>/scripts/migrate_to_upstream.sh --selfcheck-only --target /d/IQmol-upstream

# 3''. 只做代码迁移、不要资产同步时
bash <本仓库>/scripts/migrate_to_upstream.sh --apply --target /d/IQmol-upstream --no-assets
```

`--selfcheck` 会把目标树的 **95 个汉化/构建相关文件**与本仓库成果逐一 diff，
输出「完全一致 / 总数」并列出不一致文件与差异行数；有一处不一致即以退出码 **3** 结束。

脚本按序自动执行：

| 步骤 | 内容 | 规模 |
|---|---|---|
| ① | `patches/功能补丁-语言支持.patch` | 6 个文件（语言加载 / Language 偏好 / GCC15 cstdint） |
| ② | `scripts/i18n/replay_tr.py --apply` | 487 条规则 / 58 文件，新增 323 处包裹 |
| ③ | `patches/功能补丁-非机械改动.patch` | 36 个文件的逻辑改动 |
| ③.5 | `patches/功能补丁-界面资源.patch` | 22 个文件（17 个 `.ui` + `main.C` + `Math/CMakeLists.txt`） |
| ④ | `patches/功能补丁-构建层.patch` | 4 个文件（`CMakeLists.txt` / `README.md` / `.gitignore` / CI） |
| ⑤ | 资产同步 | `translations/` `share/` `doc/` `docs/` `scripts/` `resources/` |

> **顺序不可颠倒**：③ 的 diff 上下文基于 ①+② 的结果。
> 脚本已内置此顺序与逐步预检，无需手工拆解。

### 为什么迁移是六步而不是三步（重要）

早期的迁移脚本只有 ①②③ 步，只覆盖 **`src/` 下改动是纯 `.C/.h` 源码**的文件。
这留下了三类隐蔽缺口 —— 它们的共同点是「规则表抓不到、源码补丁也不管」：

| 缺口 | 后果 |
|---|---|
| **`.ui` 界面资源未迁移**（17 个） | `.ui` 里写死的按钮/标签/标题文字**保持英文** → 半汉化状态，不报错 |
| `CMakeLists.txt` 未迁移 | 构建期不调用 `lrelease` → 不生成 `zh_CN.qm` → **界面静默回退英文**，不报错 |
| `scripts/` / `translations/` 未迁移 | 目标树连 `build_windows.sh`、`i18n/` 工具链和 `.ts` 源文件都没有 |

对应补齐方式：

- **③.5** 补 `.ui` 这类**「资源文件」**改动 —— 它们不是 C++，规则表按源码原文匹配天然抓不到；
- **④** 补 `CMakeLists.txt` 这类**「上游已有但被我们整体重写」**的构建文件；
- **⑤** 补**「上游根本不存在」**的新增资产。

三者性质不同，处理方式也不同。

> **这个缺口是怎么被发现的**：2026-10-02 做端到端验证时，selfcheck 报出
> `IQmolApplication.C` 与 `InputDialog.C` 不一致。追查这 2 个文件时才发现，
> 原来的 selfcheck 基线（69 项）**本身就是由补丁清单生成的** ——
> 也就是说，"用补丁清单当基线"这个做法天然看不见补丁之外的缺口。
> 顺藤摸瓜查出 `.ui` 全类文件（17 个）从未被覆盖，随后把基线扩充到 95 项。
>
> **教训**：selfcheck 的基线必须来自「相对上游的实际 diff 全集」，
> 而不能来自「补丁清单」—— 否则就是拿考卷答案对考卷。

> 详细说明见 [`patches/README.md`](../../patches/README.md) 的
> 「③.5 界面资源补丁」与「④ 构建层补丁」两节。

## 四、冲突处理（当预检报告"有重叠"时）

脚本会列出**双方都改过的文件**。按文件类型处理：

### 4.1 源码 `.C` / `.h` 的 tr() 冲突

**冲突场景**：上游重写了某段代码，我们也给这段加了 `tr()`。

**处理原则**：
```bash
# 打开冲突文件，找到 <<<<<<< ======= >>>>>>>
# 以上游的新代码为准，然后重新套 tr()
```
- 优先保留**上游的新逻辑**（那是功能修复/改进）
- 在其上重新补 `tr("...")` 包裹
- 用 `scripts/i18n/wrap_tr.py` 可批量辅助

### 4.2 `.ui` 界面资源冲突

**冲突场景**：上游改了某个 `.ui`（新增控件、调整布局），我们也改了同一个界面。

**冲突来源**：`patches/功能补丁-界面资源.patch` 覆盖 17 个 `.ui`，
改动集中在两处 —— `<string>` 里的中文文本，以及 stylesheet 的 `font-size: Npx` → `Npt`。

**处理原则**：**以上游为基准，重新贴回**

1. 取上游的新 `.ui` 作为基准；
2. 逐个找 `<string>` 元素，把英文文本换成中文（从本仓库同名 `.ui` 里取）；
3. 在 `<styleSheet>` 段里，把 `font-size` 的 `px` 单位改为 `pt`（高分屏适配）；
4. `src/main.C` 与 `src/Math/CMakeLists.txt` 是单点改动，直接照搬。

> **若上游删除了某个 `.ui`**：先确认上游是否把它合并进了别的界面。
> 若确实已废弃，从本补丁中移除对应块，并把该文件从 `.meta.json` 的
> `covers_file_list` 里去掉。

### 4.3 `CMakeLists.txt` 冲突（最高风险项）

**冲突场景**：上游改了构建配置，我们也整体重写了这个文件。

**这是本仓库最可能冲突的文件**，因为差异极大：

| | 行数 |
|---|---|
| 上游 `af7ff60` | **224 行** |
| 本仓库成果版 | **646 行** |

也就是说，本仓库的 `CMakeLists.txt` 相对上游是**整体重写**，而非小增量。
上游只要改动这个文件的任何相邻行，`patches/功能补丁-构建层.patch` 就会应用失败。

**处理原则**：**以上游为基准，两边都要保留**

1. 取上游的新 `CMakeLists.txt` 作为基准（它含上游的功能修复、新增源文件、依赖调整）；
2. 在其上重新贴上本仓库的两段内容：

   **(a) 汉化集成段** —— 搜索 `IQMOL_STRICT_L10N`，把这一整段补回：

   ```cmake
   # ---- 严格本地化开关（IQMOL_STRICT_L10N）----
   option(IQMOL_STRICT_L10N "Fail build if zh_CN.ts has unfinished/empty translations" OFF)

   # ---- 中文本地化：构建时用 lrelease 生成 .qm ----
   find_program(LRELEASE_EXECUTABLE NAMES lrelease lrelease-qt5)
   set(IQMOL_TS_FILE ${CMAKE_CURRENT_SOURCE_DIR}/translations/zh_CN.ts)
   # ... add_custom_command POST_BUILD: lrelease + check_l10n_strict.cmake
   ```

   **(b) Windows 构建修复** —— 以下各项缺任一项都会链接失败，须逐项确认在位：

   | 修复项 | 不通的后果 |
   |---|---|
   | `QGLVIEWER_STATIC` / `YAML_CPP_STATIC_DEFINE` 宏 | `undefined reference to __imp__ZN9QGLViewer...` |
   | `OPENGL_TARGET` / `GLU_TARGET` 兜底 | `glStencil*` / `gluNewQuadric` 等符号未定义 |
   | `babelconfig.h` 兜底生成 | `elements.h` 包含 `<openbabel/babelconfig.h>` 失败 |
   | OpenBabel `BUILD_SHARED` 跟随顶层 | 插件不内联，运行时找不到 `.obf` |
   | `WHOLE_ARCHIVE` + 低版本 CMake 降级 | openbabel 静态库符号被丢弃 |
   | `STATIC_MAEPARSER` / `STATIC_COORDGEN` | Maeparser / coordgen 同类链接错误 |
   | `additional_sources` 补全 | 静态分支漏加 `asciipainter` 等源文件 |

3. 复验：

   ```bash
   bash scripts/migrate_to_upstream.sh --selfcheck-only --target /d/IQmol-upstream
   # CMakeLists.txt 应出现在「完全一致」计数中，而不是「不一致明细」
   ```

> **为什么补丁会整体失败而不是部分应用**：本补丁对同一文件是单块 hunk 序列，
> `git apply` 失败即退出并回滚该文件，**不会**产生"半汉化"的中间状态。
> 真正危险的是漏做第 ④ 步 —— 那样会得到一个能构建成功、但界面是英文的产物。

### 4.4 `translations/zh_CN.ts` 冲突

**冲突场景**：上游新增了字符串，我们的 `.ts` 与上游不同步。

**处理原则**：**不要手工合并 .ts**
```bash
# 以上游源码为准重新提取，再合并译文：
git checkout --ours translations/zh_CN.ts          # 或先备份
bash scripts/update_translations.sh                # lupdate 重新扫描
# 然后用最终译文文件覆盖（保留我们的专业术语修正）：
cp <我们的术语修正版>.ts translations/zh_CN.ts
lrelease translations/zh_CN.ts -qm translations/zh_CN.qm
```

### 4.5 上游改的构建脚本（`scripts/*.sh`）

上游 `scripts/` 下只有 5 个文件（`aws-setup.sh` / `install_packages.sh` / `mac_deploy.sh` /
`make_deb.sh` / `make_ffmpeg.sh`），**没有** `build_windows.sh`。

我们的 `scripts/` 目录**整个是新增的**（52 个文件，含 `build_windows.sh`、
`migrate_to_upstream.sh`、`sync_upstream.sh` 与 `i18n/` 工具链）。因此：

- **不存在与上游同名文件的血缘关系**，正常情况不会冲突；
- 若上游新增了同名脚本（如将来也加一个 `build_windows.sh`），**保留我们的版本**
  （它专门处理 Windows/MinGW 的坑）；
- 第 ⑤ 步资产同步用 `cp -r <本仓库>/scripts/. <目标树>/scripts/`，
  **保留目标树中上游独有的文件**，只覆盖/追加我们的。

### 4.6 `.gitignore` / `README.md` / CI 工作流

这三者都在 ④ 构建层补丁内，冲突概率远低于 `CMakeLists.txt`：

| 文件 | 冲突时处理 |
|---|---|
| `.gitignore` | **两边合并**：上游的忽略规则 + 我们的构建产物规则（`build/`、`*.o` 等） |
| `README.md` | **保留我们的中文版**；若上游 README 有重要新内容，手工并入 |
| `.github/workflows/ubuntu-2404.yml` | **两边合并**：上游的 CI 步骤 + 我们的中文化检查步骤 |

## 六、迁移后的验证清单

- [ ] 构建通过：`bash scripts/build_windows.sh --clean` → `[100%] Built target IQmol`
- [ ] **`.qm` 已生成**：`ls -l build/translations/zh_CN.qm`（④ 步生效的标志）
- [ ] 界面中文正常：启动后菜单/对话框显示中文
- [ ] **英文回退排查**：若界面是英文，先查上一条 —— 缺 `.qm` 是最常见原因
- [ ] 翻译条数：`grep -c '<message' translations/zh_CN.ts`（当前基线 2112 / 153 个 context）
- [ ] 无未译：`grep -c 'type="unfinished"' translations/zh_CN.ts` = 0
- [ ] 关键功能可用：打开分子、显示轨道、启动计算（验证静态插件未丢）
- [ ] `scripts/sync_upstream.sh --status` 显示上游新增 0（确认已吃满）
- [ ] **迁移后自动比对**：`--selfcheck` 报 `73 / 73`（或按当时基线文件数）全部一致

> **为什么把 `.qm` 单列一条**：缺 `.qm` 时 Qt 静默回退英文，**不报任何错**，
> 构建日志一片绿色。只靠"构建通过"判断会漏掉这一类事故。

## 六点五、上游大改时怎么办（selfcheck 报不一致的恢复步骤）

### 为什么会不一致

③ `功能补丁-非机械改动.patch` 是**上下文相关**的 diff：它记录了"改动行 + 前后各 3 行原文"。
上游若改了这些文件的同一处（甚至只改了邻近行），`git apply` 会出现三种情况：

| 现象 | 表现 | 危险度 |
|---|---|---|
| 整段失败 | `git apply` 报错退出，脚本因 `set -e` 中止 | 低（显式失败，看得见） |
| 部分应用 | `git apply --reject` 生成 `.rej`，部分文件没改到 | **高**（界面半中半英） |
| 静默错配 | 上下文恰好还能匹配，但改动落到了错误位置 | **高**（行为异常） |

`--selfcheck` 就是为后两种设计的兜底：**它不信任 apply 的返回值，只信最终文件比对结果**。

### 恢复步骤

1. **看清范围**：先读 selfcheck 输出，区分"不一致"与"目标树缺失"。
   - 缺失 = 该文件在新上游被删除/移动 → 跳到第 4 步；
   - 不一致 = 改动没落上或落错位置 → 继续第 2 步。
2. **定位**：对不一致文件逐个看差异，判断是"上游新增代码"还是"我们的改动没应用"。

   ```bash
   diff -u <本仓库>/src/Xxx.C /d/IQmol-upstream/src/Xxx.C | less
   ```
3. **手工补打**：在目标树里按本仓库同名文件的做法手工改一遍；
   改完重跑 `--selfcheck-only` 直到该文件消失于明细。
   若同一处上游已重构、无法照搬：**保留上游实现，重新套 tr()**，
   并把译文同步到 `translations/zh_CN.ts`（跑 `lupdate` + `lrelease`）。
4. **同步规则表 / 补丁**：上游新增的界面字符串需要新的 tr() 包裹。

   ```bash
   # 重新提取规则（基线换成新上游提交）
   python3 scripts/i18n/extract_tr_rules.py --base <新上游 sha> --out scripts/i18n/wrap_tr.rules
   python3 scripts/i18n/extract_tr_rules.py --base <新上游 sha> --verify   # 覆盖率须 100%
   # 重新生成非机械改动补丁
   diff -ru <干净上游树> <补打完成的目标树> > patches/功能补丁-非机械改动.patch
   ```
5. **复验**：回到"六、迁移后的验证清单"逐条打勾，`--selfcheck` 必须全一致。

### 预防建议

- 上游每次小版本升级就迁移一次，别攒大版本 —— 差异攒得越多，上下文漂移越严重；
- 迁移完成后立刻把新基线 sha 写进 `docs/验证记录/`，与本次 selfcheck 输出一起留档；
- CI（`i18n-tqa.yml`）会自动跑 `extract_tr_rules.py --verify`，规则表漏项会在 PR 阶段暴露。

## 七、维护者须知

## 八、我们的改动构成（决定迁移难度的关键）

对上游的修改文件做了一次分类统计（2026-10-02 实测）：

| 类型 | 数量 | 迁移时处理方式 |
|---|---|---|

> **注意**：`src/` 下的 91 个修改文件并非全由 ①②③ 覆盖。
> ①②③ 的规则表按源码原文匹配，只能抓 `.C/.h` 里的 `tr()` 包裹；
> 17 个 `.ui`、`main.C`、`Math/CMakeLists.txt` 共 22 个文件需要 ③.5 单独处理。

**结论**：绝大部分源码改动是机械的 `tr()` 包裹，可用
[`scripts/i18n/wrap_tr.py`](../../scripts/i18n/wrap_tr.py) 重新批量套用。
即使上游大改了某个文件导致冲突，处理成本也是"重新跑一遍包裹脚本 + 人工看几行"，
而非重写。

> 这也解释了我们相对上游的改动为何"轻"——不是重写功能，而是给字符串加翻译壳。

- **类 A — 字面量文本变了**：上游是拼接式 `"Computing density on grid "` + `s += ...`，
  我们改成了占位符式 `tr("Computing density on grid %1")`。规则表按原文精确查找，

> 或配合 `patches/功能补丁-语言支持.patch`（已验证可干净应用于上游）一并处理。
