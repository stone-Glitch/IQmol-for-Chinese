# 改动面最小化方案（第三层）

> **状态**：已登记为待办（WorkBuddy 任务 **#32**），尚未启动实施。
> **定位**：上游迁移能力建设的**第三层**方案，属于技术债治理，非功能修复。
> **优先级**：低于手册截图收尾（#14 / #15）。功能收尾后再启动。

---

## 一、为什么需要第三层

我们目前具备的"上游升级迁移能力"分三层：

| 层级 | 方案 | 现状 | 能力边界 |
|---|---|---|---|
| **第一层** | 共享 git 历史 + `git merge` 吸收上游 | ✅ 已具备 | 只保证"改动能合并"，不保证"无冲突" |
| **第二层** | [`scripts/sync_upstream.sh`](../../scripts/sync_upstream.sh) 预检 + 冲突预判 | ✅ 已具备 | **事后**发现冲突，无法消除冲突本身 |
| **第三层** | **改动面最小化**（本方案） | ⬜ 待实施 | 从源头减少"我们改了上游文件"这件事 |

前两层的共同点是：**承认我们会改上游文件**，然后想办法把合并做好。
第三层反过来问：**为什么非要改上游文件？**

改得越少，上游升级时的冲突面就越小。极端情况下，如果我们所有的汉化成果
都体现为"新增文件 + 极小的一行 include"，那么上游无论怎么改，合并都近乎零冲突。

---

## 二、当前改动面基线（实测）

以 `af7ff60`（上游最新，也是我们的 merge-base）为基准：

| 类别 | 数量 | 迁移时的冲突风险 |
|---|---|---|
| **修改**（`M`）的文件 | **65 个** | ⚠️ 有风险——上游改了同一文件就冲突 |
| ├ 源码 `.C` / `.h` | 42 个 | 其中 **36 个含 `tr()` 包裹（另 6 个是语言/构建逻辑）** |
| ├ 文档图片 `.png` / `.pdf` | 16 个 | 低风险（上游极少改图） |
| ├ 构建配置 `CMakeLists.txt` / `.cmake` | 3 个 | ⚠️ **中高风险**（上游常动构建） |
| └ 其他（`.ui` / `.ts` / CI / README / .tex） | 4 个 | 低-中 |
| **新增**（`A`）的文件 | **147 个** | ✅ **零风险**（上游不可能冲突） |
| **删除**（`D`）的文件 | 0 个 | ✅ 无 |

**关键结论**：147 个新增文件是"白送"的，完全不构成冲突风险。
**真正的风险集中在 65 个被修改的文件**，而其中又可进一步拆分：

- **`tr()` 包裹（36 个文件 / 178 处）** —— 机械、可脚本重放，**理论上可以做到零成本恢复**
- **构建修复（`CMakeLists.txt` 等）** —— 与上游同文件同区域，**最易冲突**
- **语言切换逻辑（4 个文件）** —— 与上游同文件，中等风险

第三层要做的，就是**逐类把这三块从"改上游源码"迁移成"附加文件"**。

## 三、三项具体工作

### A. `tr()` 包裹：从"人工改动"变成"脚本重放"

**现状问题**

`scripts/i18n/wrap_tr.py` 目前是**行号驱动的一次性脚本**：

```python
# 现状：硬编码行号，只为 MainWindow.C 服务
FILE = "/workspace/IQmol3/src/Main/MainWindow.C"
NAME_LINES = { 368: '"About"', 372: '"New Molecule"', ... }   # 行号 = 上游改动即失效
```

行号是**上游代码的一个时间切片**。上游一旦在 `MainWindow.C` 前面加了一行，
所有行号集体偏移，脚本全废 —— 而且 `assert expected in line` 会直接抛错。
更严重的是，它只覆盖 1 个文件，而我们有 36 个文件需要包裹。

**目标形态**

把它改造成**内容驱动、幂等、可全量重放**的规则集：

```
scripts/i18n/
├── wrap_tr.py            # 改造后：读规则、扫描、幂等包裹
├── wrap_tr.rules         # 新增：规则表（文件 + 目标字符串 + 匹配上下文）
└── strings/
    ├── MainWindow.C.tsv  # 每个文件的待包裹字符串清单
    ├── Layer_*.C.tsv
    └── ...
```

规则以**字符串内容**（而非行号）定位，例如：

```tsv
# file<TAB>原始字面量<TAB>包裹形式<TAB>出现次数校验
src/Main/MainWindow.C	name = "About";	name = tr("About");	1
src/Main/MainWindow.C	addMenu("File")	addMenu(tr("File"))	1
```

**幂等性要求**：脚本重复执行必须不产生差异（识别已有的 `tr(...)` 跳过）。
这是"可重放"的前提 —— 上游升级后重跑脚本，必须得到和我们手工改动**逐字节一致**的结果。

**验收方式**

```bash
# 1. 在当前分支记录期望产物
git stash                              # 或 checkout 到干净的上游基线
# 2. 从上游基线重放
python3 scripts/i18n/replay_tr.py         # 对全部 36 个文件执行规则（重放工具为 Python 脚本）
# 3. 比对：重放结果必须与我们的成果一致
git diff --stat                        # 期望：仅 tr() 相关改动，且与成果吻合
```

> **说明**：完全逐字节一致是理想目标。若某些手工改动无法规则化（例如涉及
> 上下文的复杂包裹），允许保留少量"手工补丁文件"，并在规则表中标注例外。

### B. 构建修复：从"改 `CMakeLists.txt`"变成"一行 include"

**现状问题**

根 `CMakeLists.txt` 里有若干块我们的修补，与上游内容混在一起：

| 位置 | 内容 | 风险 |
|---|---|---|
| 约 183 行 | `add_compile_definitions(STATIC_MAEPARSER STATIC_COORDGEN)` | 中 |
| 约 240-263 行 | libarchive / iconv 修补 | 中高 |
| 约 440-465 行 | `$<LINK_LIBRARY:WHOLE_ARCHIVE,...>`（openbabel / maeparser） | **高** |
| 其他 | 语言文件 `lrelease` 集成等 | 中 |

上游升级时只要动了这些文件，就可能在同一区域产生冲突。

**目标形态**

把修补集中到独立文件，根 `CMakeLists.txt` 只留一行：

```cmake
# 根 CMakeLists.txt —— 唯一的上游侵入点（就这一行）
include(${CMAKE_SOURCE_DIR}/cmake/iqmol-zh-patches.cmake)
```

```cmake
# cmake/iqmol-zh-patches.cmake —— 我们自己的文件，上游永远不会碰
# 集中所有汉化相关的构建修补，按主题分节
#   §1 静态构建宏定义
#   §2 OpenBabel / maeparser whole-archive 链接
#   §3 libarchive / iconv 修补
#   §4 翻译文件集成（lrelease）
```

**进一步：能否做到"零侵入"？**

一行 `include` 仍然是侵入。可以评估用 CMake 的钩子机制完全避开改上游文件：

| 方案 | 原理 | 侵入度 | 可行性评估 |
|---|---|---|---|
| `include()` 一行 | 在根文件加 1 行 | 1 行 | ✅ 简单可靠，推荐 |
| `CMAKE_PROJECT_INCLUDE` | `-DCMAKE_PROJECT_INCLUDE=<file>` 命令行注入，CMake 在 `project()` 后自动 include | **0 行** | ⚠️ 需所有构建入口都带上该参数（脚本可控，但 IDE 直开会漏） |
| Toolchain file | `-DCMAKE_TOOLCHAIN_FILE=...` | **0 行** | ⚠️ 语义不符（toolchain 是给交叉编译用的），但技术可行 |
| Patch 上游文件 | 构建脚本运行时替换 | 0 行（仓库内） | ✅ 已有先例（见下），最彻底 |

> **已有先例**：OpenBabel 的 `additional_sources` 修复就是这么做的 ——
> `scripts/openbabel_src_CMakeLists.txt` 是修复版文件，`build_windows.sh` 步骤 2d
> 在配置前检测并替换子模块内的 `src/CMakeLists.txt`。
> **仓库里不含对子模块文件的修改**，因此子模块升级完全不冲突。
> 这个模式可以推广到主仓库自己的构建修复上。

**评估建议**：优先做 `include()` 一行版（改动小、可读）；若追求极致，
再把 `include` 那一行也做成构建脚本注入。

### C. 语言切换逻辑：收敛到最少文件

**现状问题**

语言三态逻辑（`"system"` / `"zh_CN"` / `"en"` / 未设置）目前散落 **4 个文件**：

| 文件 | 改动内容 |
|---|---|
| `src/Util/Preferences.C` | `Language()` / `Language(QString)` 读写 + 哨兵值语义 |
| `src/Util/Preferences.h` | 接口注释同步 |
| `src/Main/IQmolApplication.C` | 启动时决定加载哪个 `.qm` |
| `src/Main/PreferencesBrowser.C` | 首选项对话框下拉框 ↔ 配置值映射 |

**目标形态**

- **理想**：收敛到单文件（例如全部塞进 `Preferences.C`，启动逻辑改为调用 `Preferences::ResolveLocale()`）
- **可接受**：若无法避免多文件，**保证改动是"整段追加"而非"修改上游行"**

  例如 `IQmolApplication.C` 中，与其在上游的 `locale = ...` 那行做修改，
  不如在附近追加一个独立函数调用：

  ```cpp
  // 上游原行保持不变
  QString locale = QLocale::system().name();
  // 我们在其后追加一行（追加行比修改行的冲突率低一个数量级）
  locale = Preferences::ResolveLocale(locale);
  ```

  这样即便上游改了 `locale` 的赋值逻辑，我们那一行追加依然干净。

### D. 建立"改动面基线"度量（配套工具）

需要一个可重复执行的脚本，每次升级后量化改动面：

```bash
bash scripts/i18n/change_surface.sh [<基准提交>]   # 规划中（尚未实现）；默认基准 af7ff60。当前改动面基线由 docs/验证记录/2026-09-18-改动面基线.md 手工维护
```

输出指标：

- 修改文件数 / 新增文件数 / 删除文件数
- 修改文件中：`tr()` 类 / 构建类 / 语言逻辑类 / 资源类 各多少
- 修改行数总和
- **可脚本重放的比例**（tr() 类 / 全部修改）—— 这个比例越高，升级越轻松

输出落到 `docs/验证记录/改动面基线.md`，作为**每次升级后的对比基准**。
若某次升级后"修改文件数"异常上升，说明有改动没有按第三层规范组织，应当回退重做。

## 四、验收标准

1. **重放能力**：存在一条可复现命令，能从干净的上游基线一键重建全部 `tr()` 包裹，
   且结果与现有成果一致（允许显式列出的例外）。
2. **冲突面下降**：在干净上游分支上执行升级流程，**冲突文件数从当前量级降到个位数**（目标 ≤ 9）。
3. **构建修复可隔离**：根 `CMakeLists.txt` 的上游侵入点 ≤ 1 行。
4. **度量可复现**：`change_surface.sh` 能输出第 D 节的全部指标，并归档为基线文档。

## 五、风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| 重构本身引入回归 | 把手工改动改成脚本重放，可能漏掉某些包裹 | 验收以"重放结果 vs 现有成果的 diff"为准，逐条核对 |
| 工作量较大 | 36 个文件 × 规则化 + 构建重构 + 语言逻辑收敛 | 拆成 A/B/C/D 四项独立推进，A 项收益最大优先做 |
| 过度工程 | 若上游长期不改这些文件，第三层收益不明显 | 上游自 v3.2.3 仅 1 提交改 3 文件，短期冲突概率低；**所以第三层优先级不高，可在下次上游大版本发布前再启动** |
| `CMAKE_PROJECT_INCLUDE` 方案易漏 | IDE 直接打开 CMake 工程时不会带该参数 | 若采用，需在 README 中显著标注，或退回 `include()` 一行方案 |

## 六、执行顺序建议

```
A. tr() 包裹脚本化（收益最大，先做）
      │  产出：wrap_tr.rules + 幂等重放脚本 + 重放一致性验证
      ▼
D. 改动面度量脚本（配套，做完 A 立刻能看出效果）
      │  产出：change_surface.sh + docs/验证记录/改动面基线.md
      ▼
B. 构建修复隔离（中等工作量）
      │  产出：cmake/iqmol-zh-patches.cmake + 根文件收敛到 1 行
      ▼
C. 语言逻辑收敛（工作量不确定，视 A/B 结果评估）
      │  产出：语言逻辑集中化或"纯追加"化
      ▼
最终验证：在上游新版本上走一遍完整升级流程，统计冲突文件数
```
