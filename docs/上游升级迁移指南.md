# 上游升级迁移指南

**目的**：上游 [`nutjunkie/IQmol3`](https://github.com/nutjunkie/IQmol3) 发布新版本后，
用最低成本把本仓库的汉化成果迁移过去。

---

## 一、基础事实（先理解，再动手）

| 项 | 事实 |
|---|---|
| 仓库关系 | 本仓库 **fork 自上游**，与上游**共享 git 历史** |
| 当前基线 | 上游提交 `af7ff60`（即我们与上游的 merge-base） |
| 我们的改动 | 相对基线 **+145 新增文件 / 68 个修改文件 / 0 删除** |
| 改动性质 | 全部是**增量修改**（汉化 tr() 包裹、构建修复、新增文档资产） |
| 迁移原理 | 因为共享历史，可直接 `git merge` 吸收上游更新，冲突通常很少 |

> **为什么能"快速迁移"**：我们的每次改动都是叠加在上游代码之上的小增量，
> 而非重写。git 能自动分辨"哪些是上游改的、哪些是我们改的"。

---

## 二、一图流程

```
上游发布新版本
      │
      ▼
scripts/sync_upstream.sh --status     ← 看差距（安全，不改任何东西）
      │
      ▼
scripts/sync_upstream.sh              ← 预检合并（不落盘，预判冲突）
      │
      ├─ 报告"无重叠" ──→ scripts/sync_upstream.sh --merge   ← 直接合并
      │
      └─ 报告"有重叠" ──→ 人工处理（见第四节）──→ 编辑后 commit
      │
      ▼
bash scripts/build_windows.sh --clean  ← 构建验证
      │
      ▼
手动确认界面中文化正常 → push
```

## 三、标准操作（绝大多数情况）

```bash
cd /d/IQmol/IQmol-src

# 1. 确认工作区干净（有改动先 commit/stash）
git status

# 2. 看上游有什么新东西
bash scripts/sync_upstream.sh --status

# 3. 预检合并（不落盘，只预判）
bash scripts/sync_upstream.sh

# 4. 若提示可干净合并，实际执行
bash scripts/sync_upstream.sh --merge

# 5. 构建验证
bash scripts/build_windows.sh --clean
```

**全程预计 10 分钟以内**（上游改动少时几分钟）。

## 四、冲突处理（当预检报告"有重叠"时）

脚本会列出**双方都改过的文件**。按文件类型处理：

### 4.1 源码 `.C` / `.h` 的 tr() 冲突

**冲突场景**：上游重写了某段代码，我们也给这段加了 `tr()`。

**处理原则**：
```bash
# 打开冲突文件，找到 <<<<<<< ======= >>>>>>>
# 以上游的新代码为准，然后重新套 tr()
```
- 优先保留**上游的新逻辑**（那是功能修复/改进）
- 在其上重新补 `tr("...")` 包裹
- 用 `scripts/i18n/wrap_tr.py` 可批量辅助

### 4.2 `CMakeLists.txt` 冲突

**冲突场景**：上游改了构建配置，我们也加了汉化集成段。

**处理原则**：**两边都要保留**
- 上游的构建配置改动（如新增源文件、改依赖）
- 我们的汉化集成段（`lrelease` 调用、`STATIC_MAEPARSER` 等静态宏、`WHOLE_ARCHIVE` 链接）

### 4.3 `translations/zh_CN.ts` 冲突

**冲突场景**：上游新增了字符串，我们的 `.ts` 与上游不同步。

**处理原则**：**不要手工合并 .ts**
```bash
# 以上游源码为准重新提取，再合并译文：
git checkout --ours translations/zh_CN.ts          # 或先备份
bash scripts/update_translations.sh                # lupdate 重新扫描
# 然后用最终译文文件覆盖（保留我们的专业术语修正）：
cp <我们的术语修正版>.ts translations/zh_CN.ts
lrelease translations/zh_CN.ts -qm translations/zh_CN.qm
```

### 4.4 上游改的构建脚本（`scripts/*.sh`）

我们的 `build_windows.sh` 等是"我们独有的重写版"，与上游同名文件无血缘关系。
若发生冲突，**保留我们的版本**（它专门处理 Windows/MinGW 的坑）。

## 五、可移植补丁集（备用方案）

若将来不再共享历史（如上游大重构），可用补丁重放：

```bash
# 生成补丁集
bash scripts/sync_upstream.sh --po
# → patches/ 下生成 N 个 .patch

# 在新基线上重放
git checkout <上游新版本>
git am patches/*.patch
```

## 六、迁移后的验证清单

- [ ] 构建通过：`bash scripts/build_windows.sh --clean` → `[100%] Built target IQmol`
- [ ] 界面中文正常：启动后菜单/对话框显示中文
- [ ] 翻译条数：`grep -c '<message' translations/zh_CN.ts`（当前基线 2106 / 153 个 context）
- [ ] 无未译：`grep -c 'type="unfinished"' translations/zh_CN.ts` = 0
- [ ] 关键功能可用：打开分子、显示轨道、启动计算（验证静态插件未丢）
- [ ] `scripts/sync_upstream.sh --status` 显示上游新增 0（确认已吃满）

## 七、维护者须知

- 本仓库的 `origin` 指向上游；汉化仓库是另一个远程（如 `chinese`）。
- **不要**把上游代码直接 `push` 到汉化仓库覆盖我们的改动。
- 每次迁移后，建议在 `docs/验证记录/` 留一条迁移记录（日期 + 上游版本 + 冲突处理）。

---

## 八、我们的改动构成（决定迁移难度的关键）

对上游的 68 个修改文件做了一次分类统计：

| 类型 | 数量 | 迁移时处理方式 |
|---|---|---|
| 源码 `.C/.h` 改动 | 42 个 | **其中 36 个（86%）含 `tr()` 包裹** |
| 构建配置（`CMakeLists.txt` 等） | 数个 | 人工合并（保留双方） |
| 文档/脚本（多为我们新增） | 145 个新增 | 直接带入，无冲突 |

**结论**：绝大部分源码改动是机械的 `tr()` 包裹，可用
[`scripts/i18n/wrap_tr.py`](../scripts/i18n/wrap_tr.py) 重新批量套用。
即使上游大改了某个文件导致冲突，处理成本也是"重新跑一遍包裹脚本 + 人工看几行"，
而非重写。

> 这也解释了我们相对上游的改动为何"轻"——不是重写功能，而是给字符串加翻译壳。

## 九、第三层：改动面最小化（长期治理）

本文描述的 `sync_upstream.sh` 属于**第二层**方案——它做的是**事后预检与冲突预判**，
能让合并过程可控，但**无法消除冲突本身**。

若想从源头把冲突面压到最低，请看 **[`docs/改动面最小化方案（第三层）.md`](改动面最小化方案（第三层）.md)**。
该方案的思路是：把 `tr()` 包裹改成脚本重放、把构建修复隔离成独立 `cmake/*.cmake` include、
把语言逻辑收敛为"纯追加"，最终让相对上游的侵入点趋近于零。

> **优先级说明**：上游自 v3.2.3 以来仅 1 次提交、改动 3 个文件，短期冲突概率低。
> 因此第三层属于**技术债治理**，建议在下次上游大版本发布前启动即可，不必急于当下。
