审查对象：stone-Glitch/IQmol-for-Chinese
审查日期：2026-10-04 ｜ 审查方式：GitHub REST API 元数据 + 直接拉取核心资产（translations/zh_CN.ts、zh_CN.qm、三个 workflow、文档索引）做静态分析

## 〇、总体判断

先说结论：这是一个完成度相当高的汉化工程，工程质量远超同类 fork。2125 条译文、0 unfinished、0 vanished、155 个 context、CI 有翻译质量门禁且门禁带自测注入（注入空译文必须被拦截），上游迁移做了双路线并实测 69/69 文件复现——这几项在业余汉化项目里很少见。

但仓库有一个会劝退贡献者和用户的硬伤：体积失控。我做审查时 git clone --depth 50 跑了 14 分钟后 RPC 断连失败（error: RPC failed; curl 56 Recv failure），这不是网络偶然，是仓库 435 MB 的必然结果。下面按优先级排列问题，P0 建议尽快处理。

## 二、P0 详解

### 1. 仓库体积失控（435 MB）

实测证据

```
$ git clone --depth 50 https://github.com/stone-Glitch/IQmol-for-Chinese.git
error: RPC failed; curl 56 Recv failure: Connection reset by peer
fatal: early EOF                    # 14 分 15 秒后失败
```

根因

| 文件 | 大小 |
|------|------|
| submodules-package/IQmol-submodules.tar.gz | 73 MB |
| submodules-package/IQmol-openbabel-fix.tar.gz | 32.6 MB |
| submodules-package/IQmol-openbabel-formats-fix.tar.gz | 1.3 MB |
| submodules-package/IQmol-openbabel-deps.tar.gz | 1.2 MB |
| submodules-package/IQmol-data-headers.tar.gz | 0.5 MB |
| 合计（当前工作树） | ≈108 MB |

历史中还曾误提交发行包（commit 493e1c7d「整理仓库结构，移除误提交的发行包」），删除文件不等于删除历史对象——这就是工作树 108 MB 但仓库 435 MB 的差值来源。

修改理由：git 的每个历史对象都会被每个克隆者下载。108 MB 压缩包 + 历史残留，让「clone 下来看看」的成本高到大多数人直接放弃；对只有 0 star 的新项目，这是致命的获客门槛。而且这些包本就是给"网络不好的人"用的——结果反而让每个人都必须下载它们。

建议方案（按推荐度）：

1. 首选：把 5 个 tar.gz 全部移出 git，作为 Release 资产上传（v3.2.4.1 已有 3 个资产，加进去即可），README 改为指向 release 下载链接。Release 资产支持断点续传、CDN 加速，比 git 传输体验更好。
2. 清理历史：迁移后用 git filter-repo --strip-blobs-bigger-than 10M 重写历史（或 BFG），把仓库压回 20 MB 量级。注意：这会重写 commit hash，需强制推送并要求所有协作者重新克隆，务必先备份、并在 README 顶部公告。
3. 若一定要留在仓库内，改用 Git LFS（补 .gitattributes：submodules-package/*.tar.gz filter=lfs diff=lfs merge=lfs -text），这样常规 clone 只拉指针文件。

责任人：@stone-Glitch（重写历史需管理员权限）｜建议窗口：下一个 Release 之前完成

### 2. GeminalOrbitalsConfigurator 四个标签缺全角冒号

实测对照（同一软件、同类面板、同样的原文）：

| 原文 | MolecularSurfacesConfigurator | OrbitalsConfigurator | GeminalOrbitalsConfigurator |
|------|-------------------------------|----------------------|-----------------------------|
| Type: | 类型： | 类型： | 类型 ❌ |
| Isovalue: | 等值面值： | — | 等值 ❌ |
| Opacity: | 不透明度： | 不透明度： | 不透明度 ❌ |
| Quality: | 质量： | 质量： | 质量 ❌ |

修改理由：四个标签在同一个面板里连着缺冒号，旁边的 Geminal(s):→「成对轨道：」却带冒号——说明是这一批翻译漏了统一后处理，不是刻意设计。用户看到的就是「类型 成对轨道：」这种参差排版，属于肉眼可见的瑕疵。

修改建议：四个译文统一补 ：；同时把 Isovalue: 统一译为 等值面值：（见下一节）。

责任人：汉化负责人

| 原文 | 冲突译文 | 建议统一为 | 理由 |

| Isovalue / Isovalue: | 等值 ／ 等值面值 | 等值面值 | "等值"在中文里有"等价"歧义；等值面的阈值标准表述是"等值面值"（isovalue） |
| Type: | 类型： ／ 类型 | 类型： | 见 P0-2 |
| Opacity: | 不透明度： ／ 不透明度 | 不透明度： | 同上 |
| Quality: | 质量： ／ 质量 | 质量： | 同上 |
| Tubes | 管状 ／ 管 | 管状 | 显示样式名，"管"单字在 UI 里像截断 |
| Number of Roots | 根数 ／ 根数量 | 根数 | CIS 计算术语，简洁优先，与"构象数"等同类格式对齐 |
| Freq. (cm⁻¹) | 频率（cm⁻¹）／ 频率(cm⁻¹) | 频率（cm⁻¹） | 中文界面统一全角括号 |
| Intens. (km/mol) | 强度（km/mol）／ 强度(km/mol) | 强度（km/mol） | 同上 |

### 6. GPL-3.0 + 静态/捆绑 Qt 的合规动作缺位

README「已知问题」里已经诚实提示了「请按 Qt LGPL-3.0 或 GPL 条款评估合规」，但只停留在"提示"，没给可执行的合规路径。

具体缺口（LGPL-3.0 对静态链接的要求）：

1. 未提供目标文件（.o/.obj）或等价的重链接材料，使接收者能替换修改后的 Qt 库重新链接；
2. 未提供 Qt 修改后的源码获取途径的书面要约（给出 Qt 官网下载页 + 版本锁定说明也可接受）；
3. Release 里未见 Qt 的 LICENSE/LGPL 文本打包（只有仓库内 THIRD_PARTY_LICENSES.md）；
4. 未说明反汇编限制与"不得阻碍用户行使重链接权"。

建议：在 Release 资产里附 Qt-LGPL-3.0.txt + 一份 RELINKING-NOTICE.md（说明用了哪个 Qt 版本、从哪下源码、怎么重链），或在 THIRD_PARTY_LICENSES.md 里补这一节。最低成本方案是改成动态链接 Qt 并随包附 DLL（你们已经在做 DLL 部署了，改动不大）。

责任人：@stone-Glitch（如需，找懂开源合规的人复核）

## 四、P2 详解

### 7. CI 工作流命名与幂等性

（a）文件名与实际不符：.github/workflows/windows-msvc.yml 里全程是 msys2/setup-msys2@v2 + MINGW64 + mingw-w64-x86_64-gcc，没有 MSVC。而 README 明确写「MSVC 路径未验证、未支持」。建议：重命名为 windows-mingw.yml（git mv 即可，历史保留）。文件名说谎会让后来者以为是 MSVC 流水线，浪费排查时间。

（b）ubuntu-2404.yml 里三步非幂等：

```bash
sudo ln -s /usr/include/openbabel3/openbabel /usr/include/      # 已存在则 fail
sudo ln -s /usr/lib/x86_64-linux-gnu/libQGLViewer-qt5.so ...    # 同上
```

在有缓存 / 复用环境 / 本地复现时会直接报错。建议改为 `sudo ln -sfn ...` 或加 `[ -e target ] || ln -s ...`。

（c）建议补两条 CI：

- macOS 构建验证（README 声称支持 macOS 三平台，但 workflow 只有 Linux + Windows，macOS 路径零验证）；
- 一个"仅文档/翻译改动"的 path filter，避免改 README 也触发 4 个平台 ×2 配置的完整编译（省 runner 额度）。

责任人：@stone-Glitch

### 8. 子模块离线包无版本漂移校验

CI 走的是「解包 submodules-package/IQmol-submodules.tar.gz」，不是 git submodule update --init。README 声称"版本与 .gitmodules 记录的 commit 完全一致"，但没有任何自动校验：上游子模块 bump commit、或重新打包时漏更新，CI 会静默用一个旧版本编出包，且完全不报错。

建议：在包里放一个 MANIFEST.json（每个子模块的 path + commit sha + 打包时间），CI 解包后用脚本比对 .gitmodules 的 gitlink sha，不一致即 fail。成本约 30 行 shell，能挡住一类很难查的"莫名其妙的运行时 bug"。

责任人：@stone-Glitch

### 9. 在翻译层修拼写——改不掉的三处

| 原文 | 译文 | 问题 |
|------|------|------|
| Lable6 | Label6 | 这是（疑似）QLabel 的 objectName。objectName 不经过 tr()，翻译文件里改它完全不生效；要改必须改源码/.ui |
| InChi | InChI | 若只是显示标签则生效，但同类术语在别处可能仍是 InChi，会造成新的不一致 |
| mol2 | Mol2 | 文件格式名大小写不统一 |

修改理由：翻译文件是"按原文精确匹配"的映射表，不是源码修正工具。在这里修拼写有三个副作用：① 词义上修不好（objectName 不走翻译）；② 下次 lupdate 抽取时原文没变，译文差异会被当成人工改动保留，掩盖真实问题；③ 真正需要修的是源码，改翻译会让人误以为已经修完。

建议：确认这 3 处的真实位置——objectName 类的改源码（可进 功能补丁-非机械改动.patch），显示文案类的先统一源码大小写再重跑 lupdate。

责任人：汉化负责人（定位）+ @stone-Glitch（改源码）

### 10. 71 处硬编码英文残留，TQA 门禁管不到

docs/汉化工程/工程待办与现状登记.md 已登记：约 71 处硬编码英文未进入 tr() 流程，其中 13 个电荷模型术语译法未定。

而现有 i18n-tqa.yml 的门禁项是：TS 未完成条目 / 空译文 / qm 缺失 / 源码—翻译漂移率 / 致命术语错误 / 规则表覆盖率——全是"翻译文件侧"的指标，没有"源码侧覆盖率"指标。也就是说，源码里新增一个没包 tr() 的 UI 字符串，CI 全绿。

建议：给 scripts/i18n/tqa.py 加第 7 项：扫描 src/ 中疑似用户可见字符串（QStringLiteral/直接字面量传给 setText/setToolTip/QMenu::addAction 等）未被 tr() 包裹的数量，设阈值（如 ≤71 且不得增加）而非要求 0，先卡住"不再恶化"，再逐步清零。这和你们已有的门禁自测思路（"不能是永远绿的摆设"）是一致的。

责任人：汉化负责人

## 五、P3 详解

### 11. 可发现性几乎为零

当前：0 star、0 fork、无 topics、无 homepage、无 About 描述之外的英文简介。而上游 nutjunkie/IQmol3 是英文项目，中文用户搜索"IQmol 中文"大概率搜不到这里。

低成本三件事：

1. 仓库 topics 填：iqmol、chemistry、molecular-visualization、qt5、chinese-localization、i18n、qchem、简体中文；
2. Homepage 填 https://www.iqmol.org，About 补一句英文（如 Simplified Chinese localization of IQmol3 — 2125 translated strings, 34-page Chinese manual.），让搜索能命中；
3. 去上游提 Issue / PR 反哺：把 20 个源文件的 tr() 包裹、-extensions C,ui 这个坑、GLObject.h 导致 lupdate 误标 vanished 的发现提交给 nutjunkie/IQmol3。这类贡献对上游有真实价值，也是这个项目最自然的引流入口——比在 B 站发视频更持久。

### 12. 发布资产缺校验与签名

README 说"校验请使用发布说明中的 SHA256"，但 Release 里未见 SHA256SUMS 资产，SECURITY.md 也未给出校验流程。建议：每次打 tag 时由 CI 自动生成 SHA256SUMS.txt 并作为 Release 资产上传（一行 shell：sha256sum *.zip *.tar.gz > SHA256SUMS.txt）。

## 六、做得好的地方（别改）

审查不能只挑刺，以下几项建议在后续重构中完整保留：

1. TQA 门禁带自测注入：i18n-tqa.yml 最后一步主动把一条 finished 译文改成空，验证 --gate 必须返回非 0，再还原验证重新变绿。「门禁不能是永远绿的摆设」这条设计思想很到位。
2. 上游迁移双路线 + 实测 69/69 复现：migrate_to_upstream.sh（重放）与 sync_upstream.sh（merge）两条路都做了 --check 预检，这是 fork 类项目最难也最容易偷懒的部分。
3. 踩坑记录写进代码注释：lupdate -extensions C,ui 的参数顺序、setup-msys2 不能开 update: true、qt5-translations 与 qt5-tools 是两个包——这些注释能省下后来者几十小时。
4. 翻译部署三层修复（reA22A）+ 静态自检脚本：qm 放两处、源码多路径搜索、run.sh 切目录，并用 check_translation_deploy.py 在不构建的情况下防回退。
5. 文档中心分层：doc/（上游英文手册源）与 docs/（本仓中文文档）只差一个字母，README 专门做了醒目警示——这种"我预见你会踩"的文档很稀缺。
