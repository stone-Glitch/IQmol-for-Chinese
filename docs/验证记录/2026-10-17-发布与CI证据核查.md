## 一、CI 平台覆盖（结论：实际两平台，macOS 缺失）

| 平台 | 工作流 | 构建矩阵 | 产物 / 校验 | 状态 |
|---|---|---|---|---|
| Linux x86_64 | `ubuntu-2404.yml` | `ubuntu-24.04` × {Debug, Release} | `cmake --build` + `ctest` | ✅ 已定义 |
| Linux arm64 | `ubuntu-2404.yml` | `ubuntu-24.04-arm` × {Debug, Release} | 同上（ARM 自带 gfortran，已适配） | ✅ 已定义 |
| Windows x64 | `windows-mingw.yml` | `windows-latest` (MinGW-w64) | `build_windows.sh` + `package_windows.sh`（含自包含性/系统 DLL/sqldrivers/翻译齐备/目录嵌套 五道自检）→ `.7z` + `.zip` + `SHA256SUMS.txt` | ✅ 已定义 |

| 翻译门禁 | `i18n-tqa.yml` | 任意 push/PR | unfinished=0 / 空译文阻断 / 漂移≤5% / 规则表覆盖 100% | ✅ 已定义 |

- **实测证据缺口**：以上为「工作流定义能保证什么」，非「远程已跑绿」。CI 实际运行结果（green check）需 `gh run list` / Actions 页面授权查看。
- **macOS 不一致**：`docs/构建与打包/Build.md` 与 `./configure` 均宣称「三平台（Linux/macOS/Windows）」，但仓库 CI 仅有 Linux + Windows 两条工作流，**macOS 既无 CI 也无构建证据**，属文档口径与现实的偏差。若需补齐「三平台证据」，须新增 `macos-latest` 工作流（GitHub 托管 macOS runner），并经至少一次成功运行验证；在授权到位前仅能先起草工作流草案。

## 二、Release 发布状态（结论：已发布，但命名/校验和需重发修正）

经 `docs/构建与打包/release_notes.md` 记录的 `api.github.com` 实测：

| Release | 状态 | 附件 |
|---|---|---|
| `v3.2.3-zh_CN` | 已发布 | `IQmol-linux-x86_64.tar.gz`、`IQmol-win64-3.2.3-zh_CN.zip`、`SHA256SUMS.txt` |
| `v3.2.4.1-zh_CN` | **已发布（当前最新）** | `IQmol-win64-3.2.3-zh_CN.zip`、`IQmol-win64-3.2.3-zh_CN.7z`、`SHA256SUMS.txt` |

**两处已知的发布卫生问题**（不影响功能）：

1. **资产命名错位**：最新 Release 的附件仍叫 `...3.2.3...zip/.7z`，但包内容为 v3.2.4.1 源码所出。
   - **根因**：构建时 `CMakeLists.txt` 的 `project(... VERSION ...)` 仍是 `3.2.3`，而 `scripts/package_windows.sh:61` / `package_linux.sh:81` 的版本号**已从 CMakeLists 动态读取**（`sed` 提取 `x.y.z`）。#145 已将版本字段统一为 `3.2.4.1-zh_CN`，故**重新构建即自动产出正确命名 `IQmol-win64-3.2.4.1-zh_CN.*`**，无需改打包脚本。
2. **仓库内 `docs/构建与打包/SHA256SUMS.txt` 记录的是 v3.2.3 校验和**；v3.2.4.1 的 `SHA256SUMS.txt` 以 Release 页附件为准，`docs/` 副本未同步。
