## 一、补丁未进入构建（configure 跳过判定盲区）

### 现象

Windows（MinGW64）重跑 `scripts/build_windows.sh` 链接 `bin/IQmol.exe` 时报：

```
libopenbabel.a(asciiformat.cpp.obj): undefined reference to `OpenBabel::ASCIIPainter::ASCIIPainter(int, int, double)'
libopenbabel.a(painterformat.cpp.obj): undefined reference to `OpenBabel::CommandPainter::CommandPainter(std::ostream&)'
libopenbabel.a(maeformat.cpp.obj): undefined reference to `__imp__ZN11schrodinger3mae6ReaderC1ESt10shared_ptrISiEy'
libopenbabel.a(wlnformat.cpp.obj): undefined reference to `NMReadWLN(char const*, OpenBabel::OBMol*)'
```

符号集合与上一轮**逐条一致** → 同一报错重现，通常不是「上次没修对」，而是「上次的修复没进构建」。

### 排查

**① 补丁本身对不对**：取子模块锁定提交 `ea4710f04120df713a6806ffb56baae29f16f58f` 对比——

```bash
git -C <openbabel-repo> show ea4710f:src/CMakeLists.txt   # 上游真实文件
diff <上游文件> scripts/openbabel_src_CMakeLists.txt       # 对比修复版
```

**前 183 行完全一致**，差异仅在静态分支 `foreach` 内插入 13 行：

```cmake
else(BUILD_SHARED)
  include(formats/formats.cmake)
  foreach(format ${formats})
    set(openbabel_srcs ${openbabel_srcs} formats/${format}.cpp)
    # ← 上游到此为止：只读 formats/xxxformat.cpp，从不读 xxxformat_additional_sources
    if(NOT format STREQUAL "inchiformat")                                   # ┐
      set(openbabel_srcs ${openbabel_srcs} ${${format}_additional_sources}) # │ 修复
    endif()                                                                # ┘
  endforeach(format ${formats})
```

缺失符号来源（读上游真实 `src/formats/formats.cmake`）：

| format | `additional_sources` | 缺失符号 |
|---|---|---|
| `asciiformat` | `../depict/asciipainter.cpp` | `OpenBabel::ASCIIPainter::*` |
| `painterformat` | `../depict/commandpainter.cpp` | `OpenBabel::CommandPainter::*` |
| `wlnformat` | `wln-nextmove.cpp` | `NMReadWLN()` |

→ 补丁逻辑正确。**② 补丁进没进构建**：脚本在 configure 前覆盖修复版（步骤 2d，第 220 行），顺序正确；盲区在步骤 4 的跳过判定：

```bash
# 条件一：构建目录健全性
if [ ! -f "$BUILD_DIR/CMakeCache.txt" ] || [ ! -f "$BUILD_DIR/Makefile" ]; then NEED_CONFIG=1
# 条件二：只有【顶层 CMakeLists.txt】比 CMakeCache.txt 新才重配
elif [ "$SRC_DIR/CMakeLists.txt" -nt "$BUILD_DIR/CMakeCache.txt" ]; then NEED_CONFIG=1; fi
```

`_cfg_fingerprint()` 同样只 `grep "$SRC_DIR/CMakeLists.txt"`。**两者只盯顶层，而补丁改的全是 `modules/` 下文件**：

| 步骤 | 改动文件 | 在判定范围内 |
|---|---|---|
| 1 | `modules/CMakeLists.txt` | ❌ |
| 2b | `modules/openbabel/CMakeLists.txt` | ❌ |
| 2c | `modules/openbabel/data/CMakeLists.txt` | ❌ |
| 2d | `modules/openbabel/src/CMakeLists.txt` | ❌ |

### 根因

```
上次 configure 成功 → CMakeCache.txt + Makefile 存在
 → 步骤 2d 覆盖了 modules/openbabel/src/CMakeLists.txt ✅（内容对了）
 → 顶层 CMakeLists.txt 没变 → NEED_CONFIG=0 → 跳过 configure ❌；指纹也没触发
 → make 沿用旧 build/modules/openbabel/src/CMakeFiles/*.make（只有 formats/xxxformat.cpp）
 → asciipainter.cpp / commandpainter.cpp / wln-nextmove.cpp 从未编译 → undefined reference 复现
```

日志吻合：走到 `[100%]` 才失败（旧产物完整，只缺 3 个 `.o`）；`libMain.a` 链接成功（`Main` 不依赖这些符号）。

### 处置

新增**补丁指纹**：记录补丁文件当前是否「已修」，与上次不一致即强制 configure。

```bash
_patch_fingerprint() {
  local _mods=0 _ob_root=0 _ob_data=0 _ob_src=0
  [ -f "$MODULES_DIR/CMakeLists.txt" ] && _mods=1
  grep -q 'NOT TARGET uninstall'       "$MODULES_DIR/openbabel/CMakeLists.txt"      && _ob_root=1
  grep -q 'pregen'                     "$MODULES_DIR/openbabel/data/CMakeLists.txt" && _ob_data=1
  grep -q 'format}_additional_sources' "$MODULES_DIR/openbabel/src/CMakeLists.txt"  && _ob_src=1
  printf 'PATCH_STATE MODS=%s OB_ROOT=%s OB_DATA=%s OB_SRC=%s' "$_mods" "$_ob_root" "$_ob_data" "$_ob_src"
}
```

用「语义标记」而非「记录本次执行了哪些补丁」：动作记录型在执行轮/非执行轮间抖动 → 每轮都 re-configure；语义标记型打补丁前 `0000` → 后 `1111`，**恰好变化一次即触发**，之后稳定跳过。

### 验收（仿真 6 场景全过，用上游真实文件 `ea4710f`）

| # | 场景 | 期望 | 实测 |
|---|---|---|---|
| 1 | 三补丁未应用 → 首轮 | 触发重配 | ✅ `★ 触发` `0000 → 1111` |
| 2 | 紧接着再跑 | 跳过 | ✅ `· 跳过` |
| 3 | 第三次跑 | 跳过（稳定） | ✅ `· 跳过` |
| 4 | submodules 包把 src 覆盖回未修版 | 触发重配 | ✅ `★ 触发` `OB_SRC=0` |
| 5 | 恢复补丁后再跑 | 触发一次 | ✅ `★ 触发` `OB_SRC=1` |
| 6 | 连续两次 | 跳过 | ✅ `· 跳过` `· 跳过` |

端到端（2b+2c+2d 全跑）：`[步骤2b/2c/2d] 已修复` → `[补丁指纹判定] ★ 触发重新 configure` → `PATCH_STATE MODS=1 OB_ROOT=1 OB_DATA=1 OB_SRC=1`。

### 结论

直接重跑即可（脚本会因指纹变化自动重新 configure）；`--clean` 为彻底重来（configure 约 1~5 分钟，编译约 20~40 分钟）：

```bash

bash scripts/build_windows.sh --clean    # 彻底重来
```

预期日志：①`==> 检测到子模块补丁状态变化（补丁已应用到源码树，但尚未反映到构建配置），自动重新 configure...`；②`asciipainter.cpp`/`commandpainter.cpp`/`wln-nextmove.cpp` 编译行；③`[100%] Built target IQmol`。

### 排查与根因（语言切换「跟随系统」是假的）

**现象**：issue4 的「界面语言」下拉中，「跟随系统」与「中文」行为完全相同——系统为英文时选「跟随系统」仍强制中文。
**根因**：`Preferences::Language()` 用**空串**表示跟随系统，`loadTranslations()` 无法区分「显式跟随系统」与「首次运行」：

```cpp
QString pref = Preferences::Language();
if (!pref.isEmpty()) { locale = pref; }
else if (!locale.startsWith("zh")) { locale = "zh_CN"; }  // ← 两者都落这里
```

### 处置

引入哨兵 `"system"`，区分四态：

| 取值 | 含义 | 行为 |
|---|---|---|
| `"system"` | 显式跟随系统 | 用系统 locale，无翻译文件则回退英文 |
| `"zh_CN"` | 强制中文 | 加载 zh_CN |
| `"en"` | English | 加载 en（通常无文件→英文） |
| 未设置 | 首次运行 | 保持汉化默认（非中文环境也显示中文） |

改动：`src/Util/Preferences.C`（`Language()` 语义）、`Preferences.h`（注释同步）、`src/Main/IQmolApplication.C`（`loadTranslations()` 四态）、`src/Main/PreferencesBrowser.C`（下拉用 `"system"` 而非空串）。C++ 单元测试 8 场景全过：

```
PASS pref=''       sys=en_US -> zh_CN   （首次运行+英文系统=汉化默认中文）
PASS pref=''       sys=zh_CN -> zh_CN     PASS pref='en'     sys=zh_CN -> en
PASS pref='en'     sys=en_US -> en        PASS pref='zh_CN'  sys=en_US -> zh_CN
PASS pref='system' sys=en_US -> en_US ★   PASS pref='system' sys=zh_CN -> zh_CN
PASS pref='system' sys=ja_JP -> ja_JP
```

## 经验沉淀

1. **「打了补丁」≠「补丁生效」，判定覆盖面必须与改动面匹配**：`*.make`/`build.make` 是补丁与编译之间的缓存层，改了源码树输入却不重建它等于没改；判定只看顶层 `CMakeLists.txt` 而补丁改 `modules/` 子目录文件，就会静默失效。
2. **同一报错重现时，先怀疑「修复未进入构建」而非「方向错」**：先验证补丁逻辑（读上游真实源码逐行对比），再查构建流程。
3. **补丁指纹用语义标记而非动作记录**：动作型在执行轮/非执行轮间抖动 → 每轮 re-configure；语义型 `0000 → 1111` 只触发一次。
4. **补丁生效自查法**：编译日志应出现被新增源文件的编译行（如 `asciipainter.cpp`/`commandpainter.cpp`/`wln-nextmove.cpp`）与「检测到子模块补丁状态变化…自动重新 configure」；只有 `[100%] Built target` 而无新增编译行 = 补丁未进构建。
5. **报错文案可能误导**：`Failed to load force field` 提示「`BABEL_DATADIR` 可能没设对」，实际常是构建配置问题（静态库插件自注册对象被链接器丢弃）；含「环境变量/路径」提示时，先确认构建配置生效再查运行环境。
6. **文档无强制联动时，改动后须补「口径 + 索引 + 链接」核对**：条数以 `grep -c '<message'` 实测（日志实录保留原文并加注）、新记录补索引、相对链接按实际层级校验。
