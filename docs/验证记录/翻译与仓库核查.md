## 一、tr() 包裹重放机制验收
**日期** 2026-09-19　**类型** 方案验收（第三层方案 A 项）
**结论** ✅ 通过。端到端重建 35/42 源码文件完全一致，规则覆盖率 100%，幂等性双向验证成立。

### 1.1 要解决的问题
上游升级后，相对 `af7ff60` 的汉化改动有两层风险：`git merge` 在翻译包裹密集文件上大量冲突；即使合并成功，上游新代码也可能覆盖包裹。原 `wrap_tr.py` 是**行号驱动**的一次性脚本（只服务 `MainWindow.C`、硬编码行号表），上游插入一行即全部失效。**目标**：把包裹改造成**内容驱动、可幂等重放**的规则表，升级后一条命令重建。

### 1.2 改动面实测（口径修正）

|---|---|---|---|

| 功能补丁（语言加载 / 偏好 / GCC15 兼容） | 6 | — | `patches/功能补丁-语言支持.patch` |

### 1.3 机制要点（4 个关键设计）
**① 三元组键：同一字面量多形态。** `MainWindow.C` 的 `Save` 同时以两种形态出现，规则表键为 `(路径, 字面量, 形态)`，两处各占一行；早期二元组键漏掉其中一种，本次修正后覆盖。

```cpp
messageBox.addButton(tr("Save"), QMessageBox::AcceptRole)   // call:messageBox.addButton
name = tr("Save");                                           // bare
```

**② count 语义 B：最终包裹总数（幂等的关键）。**

```cpp
// ExcitedStatesConfigurator.C
第 341 行  setLabel(tr("Rel. Strength"))   ← 上游已自带
第 345 行  setLabel("Rel. Strength")       ← 裸的，由我们包裹
```

语义 A（数 diff 新增行的包裹数）→ `count=1` → 重放判定"仍有 1 处未包" → **再包一次，不幂等**；语义 B（成果文件中最终包裹总数）→ `count=2` → 重放补 `2-1=1` 处 → 幂等 ✅。

**③ 补足式 vs 构造式**

| 形态 | 上游原文 | 动作 |
|---|---|---|
| `call:` / `bare` | 常有部分 `tr()` | **补足**裸字面量的包裹 |
| `translate:<上下文>` | 恒为裸字面量 | **构造** `QCoreApplication::translate(...)`，并自动注入 `#include <QCoreApplication>` |

新增 `translate:` 形态专为 `UndoCommands.C` 而设（`QUndoCommand` 非 QObject，没有 `tr()`），使残余差异从 **21 行降至 1 行**。

**④ 函数上下文精确定位（品牌名陷阱）。** 不能用"全局排除名单"处理品牌名——会漏掉该包的那处；正确做法是尊重 `call:` 上下文的函数名约束。

```cpp
setWindowTitle(tr("IQmol"));                       // 包裹
QMessageBox(..., "IQmol", tr("Save Changes?"));    // 不包裹
```

该文档构造了三步证据，①②的事实都对，但**推论都断了**：

| 文档证据 | 实测情况 |

## 三、Linux 分发包中文翻译加载失败定位（reA22A）
**发现日期** 2026-09-24　**影响产物** `submodules-package/linux-build/IQmol-linux-x86_64.tar.gz`　**严重级别** **高**（中文界面静默失效，用户看到英文）
**状态说明** 原始定位结论见下；据外部说明已于 **2026-09-25 修复**，但原文未记录实际采用的修复细节，故此处仅保留定位与候选方案。

### 3.1 现象与复现
在 Linux 预编译包上无头启动 IQmol，日志出现 `[i18n] No translation file found for: "zh_CN"` —— **中文翻译未加载，界面回退英文**，尽管翻译文件就在包内。

```bash
tar -xzf IQmol-linux-x86_64.tar.gz
cd IQmol-linux-x86_64/bin
export LD_LIBRARY_PATH=../lib:$LD_LIBRARY_PATH
export QT_QPA_PLATFORM=offscreen
./IQmol --clear-jobs
# 观察输出中的 [i18n] 行：预期 Loaded translation，实际 No translation file found for: "zh_CN"
```

### 3.2 根因
翻译文件位置与程序搜索路径不匹配。`src/Main/IQmolApplication.C:114-118` 的搜索路径为（`applicationDirPath()` = 可执行文件所在目录 = `bin/`）：

```cpp
QStringList searchPaths;
searchPaths << QApplication::applicationDirPath() + "/translations"   // bin/translations/
            << QApplication::applicationDirPath()                     // bin/
            << QDir::current().filePath("translations")               // cwd/translations
            << QDir::currentPath();                                   // cwd/
```

而包内实际布局为：

```
IQmol-linux-x86_64/
├── bin/IQmol                  ← applicationDirPath() = .../bin
├── translations/zh_CN.qm      ← 实际位置（在 bin 的上一级）
├── lib/
└── share/
```

**`bin/translations/` 不存在**，且从 `bin/` 启动时 `cwd/translations` 也指向 `bin/translations/`（若用户 `cd bin` 后运行）——两条路径均落空。
> 注：Windows 部署时 `deploy_windows.sh` 会把 `zh_CN.qm` 复制到 `build/bin/translations/`，与 `applicationDirPath()` 一致，故 Windows 包不受影响；Linux 打包脚本未做同样处置。

### 3.3 验证：修正后即加载成功
```bash
mkdir -p bin/translations
cp translations/zh_CN.qm bin/translations/
cd bin && ./IQmol --clear-jobs
# → [i18n] Loaded translation: "zh_CN"     ✅
```

**根因确认**：仅需把 `.qm` 放到 `bin/translations/`，加载即成功。

### 3.4 候选修复方案（原文提出，均未标注为已实施）
**方案 A（推荐）：打包脚本补一步** —— Linux 打包时把 `translations/*.qm` 复制到 `bin/translations/`：

```bash
mkdir -p "$STAGE/bin/translations"
cp "$STAGE"/translations/*.qm "$STAGE/bin/translations/"
# 同时保留包根的 translations/ 以兼容旧布局与 run.sh
```

**方案 B：源码侧增加搜索路径** —— 在 `loadTranslations()` 的 `searchPaths` 中增加 `../translations`，兼容包根布局：

```cpp
searchPaths << QApplication::applicationDirPath() + "/translations"
            << QApplication::applicationDirPath() + "/../translations"   // 新增
            << QApplication::applicationDirPath()
            ...
```

> 原文建议**两者都做**：A 立即修复产物，B 提升对布局差异的鲁棒性。

### 3.5 回归验证清单与工具
修复后须确认：① 日志出现 `[i18n] Loaded translation: "zh_CN"`（无 `No translation file found`）；② `scripts/i18n/sampler.py --log <日志>` 检查 `L_qm = 1.0`；③ GUI 环境下主菜单显示中文。

```bash
python3 scripts/i18n/sampler.py --log iqmol.log          # 判定 QM 加载率 L_qm
python3 scripts/i18n/sampler.py --strings ui_strings.txt # 命中率 H_qm / 英文残留率 E_r
```

该工具是 TQA 指标体系 W4 层的实现，用于把 `tqa.py` 中「未测量」的运行时指标变为「已测量」。

### 5.5 运行中文版
**真实桌面**（Linux / macOS / Windows）：直接运行 `IQmol`，中文翻译自动加载。**无显示环境**（CI / 沙箱）：需虚拟显示 + 软件 OpenGL：

```bash
xvfb-run -a -s "-screen 0 1280x1024x24" env \
  QT_QPA_PLATFORM=xcb \
  BABEL_LIBDIR=/usr/lib/x86_64-linux-gnu/openbabel/3.1.1 \
  BABEL_DATADIR=/usr/share/openbabel \
  LANG=zh_CN.UTF-8 LC_ALL=zh_CN.UTF-8 \
  ./IQmol
```

| 环境变量 | 作用 |
|---|---|
| `BABEL_LIBDIR` | 覆盖 OpenBabel 插件目录。IQmol 默认 `/usr/lib/openbabel/3.1.1`，**Ubuntu 实际为 `/usr/lib/x86_64-linux-gnu/openbabel/3.1.1`**，必须覆盖否则报 `Unable to find OpenBabel plugins` |
| `BABEL_DATADIR` | OpenBabel 数据目录（原子类型、力场参数等） |
| `LANG` / `LC_ALL` | 设置中文区域；本汉化为「非中文时默认中文」，故即便未设也会加载 `zh_CN` |

**翻译加载逻辑**（`IQmolApplication::loadTranslations()`）：① 加载 Qt 基础翻译（`qt_<locale>.qm`，标准对话框按钮等）；② 取 `QLocale::system().name()`，**若非 `zh` 开头则强制 `zh_CN`**（满足"默认中文界面"）；③ 按序搜索 `zh_CN.qm`：`applicationDirPath()/translations` → `applicationDirPath()` → `currentPath()/translations` → `currentPath()`。

## 六、经验沉淀
1. **脚本化改动必须内容驱动、可幂等。** 行号驱动的 `wrap_tr.py` 在上游插入一行即全面失效；改用 `(路径, 字面量, 形态)` 三元组规则表后才实现"一条命令重建"。凡需长期跟随上游的本地改动，都不应依赖行号这类易漂移坐标。
2. **计数口径决定幂等性。** 规则表 `count` 须取"成果文件中最终包裹总数"（语义 B），而非"diff 新增几处"（语义 A），否则重放会反复补包。写宣告式规则前先想清它描述的是"增量"还是"终态"。
3. **最小复现用例必须包含真实上下文。** 第三方评测用不含 `#include "Qui.h"` 的 g++ 最小用例得出"必然构建失败"，实为人为构造报错；脱离 include、命名空间、链接环境的片段验证不能作为缺陷结论依据，P0 级论断应有全工程编译支撑。
4. **关键事实要交叉双源验证。** `Qui.h` 经本地源码树与 GitHub raw 双向比对（均 1587 字节 / 60 行）才排除"本地解压不全"；同一作者此前确有 tarball 未解压完的记录。来自可能损坏的检出/解压的单点取样不可直接下结论。
5. **打包布局要与运行时搜索路径对齐。** `applicationDirPath()/translations` 与包根 `translations/` 错配导致中文静默失效，Windows 因 `deploy_windows.sh` 复制到位而不受影响；宜"打包脚本补一步"+"源码侧增加 `../translations` 兜底"双管，前者修产物、后者提鲁棒性。
6. **移植的失败点集中在平台差异常量。** Ubuntu 上 QGLViewer 库名带 `-qt5`、OpenBabel 插件实际路径为 `/usr/lib/x86_64-linux-gnu/openbabel/3.1.1`，均与上游默认值不同；工具同理（`qttools5-dev` 才含 CMake 配置，`-tools` 不含）。跨平台工程应把这些差异固化为变量或 `find_program` 结果，而非硬编码。
7. **翻译覆盖率死角要人工兜底并脚本防退化。** `lupdate` 提取不到拼接串与宏常量（4 个 context 需手工补条目），且这些拼接构造超出机械包裹能力，只能重写为 `tr("A %1").arg(var)`；补好后由 `update_translations.sh` 常态化移除误标 vanished，防止再次退化。
