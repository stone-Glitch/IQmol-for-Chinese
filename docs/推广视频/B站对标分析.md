## 二、硬指标对照（同口径逐帧实测）

分析脚本：`scripts/video/shot_density.py`（降采样到 160×90 灰度，逐帧求相邻帧平均绝对差，超阈值记一次变化，0.4 秒内合并）。

> ⚠️ **阈值是这套方法最大的坑。** 各视频帧差分布差异极大：
>
> | 视频 | p99 | max |
> |---|---|---|
> | 对标 B 沉浸式翻译 | 27.95 | 201.0 |
> | 对标 A UVR5 | 19.74 | 159.0 |
> | 对标 C 分屏读顶刊 | 15.22 | 115.5 |
> | 我们（录屏 + 大字卡） | 5.35 | 164.9 |
>
> 早期版本固定用阈值 8，导致我们这种低对比画面**一次变化都测不到**，自检误报"首次变化 11.96秒"，而实际第 1.5 秒就有变化。现默认阈值 1，并同时输出 1/3/8 三档交叉验证。

| 段4 三段标注裁剪区重框（时间差分定位动作区） | 修复"46 秒处看不到鼠标操作"：原裁剪只框静态工具栏小角，菜单展开和 Q-Chem 对话框弹出全被裁掉 |
| **段4 三组素材真实重录**（缓动光标 + 点击波纹） | 不再是静态录屏：光标 smoothstep 缓动 ~0.8s 划过画面，每次点击叠 0.8s 橙色扩散波纹；画面变化 24 → 25 次 |
| 波纹叠加改用 `setpts` 平移时间轴 | 修掉"波纹根本没叠上"：ripple 只有 0.8s，overlay 到 3.6s 时该流早已 EOF，默认只重复最后一帧（透明度≈0），实测差异仅 81 像素 |
| `start_app` 清理 X 僵尸窗口 | 修掉"点了没反应"：IQmol 非正常退出会残留 X 窗口，实测一个"元素周期表" popup 正好盖住 4a 的点击点 (444,82)，把后续点击全吃了 |
| 录制驱动回退到 llvmpipe | softpipe 虽能修好 GL 重绘（切换样式 Δ=36），但 UI 点击整体失效（popup 区 std 恒定 82.3、Q-Chem 不弹），素材直接废掉；两害相权取 llvmpipe |
| `verify_clicks` 自动校验每次点击 | 点完立刻做区域帧差，MAE < 0.2 就报警——避免"点了但没生效"的素材混进成片 |
| **4c 放弃"配置分子"对话框，改拍拖拽旋转 + 滚轮缩放** | 那个对话框一打开画布就**永久清空**（分子区 std 22.8→0.0，切换样式 Δ=0.00，Escape 关闭也不恢复）。llvmpipe / softpipe / swrast **三驱动实测完全一致**，是软件渲染的共性缺陷，不是驱动选择问题。改用画布自身的拖拽/滚轮，分子全程保留（std 22.7–27.8） |
| **4c 录制前加"彩排"** | ffmpeg x11grab 持续抓屏吃满 CPU，IQmol 刚开始几秒忙着渲染，**第一次拖拽被吞掉**（正式录制前 2.5s Δ≈0.02，完全静止；不录制时同样拖拽 Δ=11.9 正常）。先把整套动作不录制跑一遍热状态，正式录制就能接上——动态区间 9/15 → **7/7**，最小 Δ 从 0.02 升到 17.5 |
| **4c 单独给 12 秒时长 + `check_clicks_in_range` 自查** | 彩排暴露出第二个问题：录制期间每个 xdotool 调用被拖慢约 1.5 倍，动作序列理论 7.9s 实际跑 11.7s，8 秒素材把末尾两次滚轮截掉（点击时刻 11.24s/11.70s 落在素材外）。verify_clicks 查不出这个（它只看素材内的帧），必须按时间戳单独自查 |
| **所有 ffmpeg 调用加 `-nostdin`** | 修掉合成脚本在信息卡阶段静默退出（exit 254）：`while read ... done < cards.tsv` 的重定向让 tsv 成为整个子进程树的 stdin，ffmpeg 默认从 stdin 读、每跑一次推进文件偏移，下一轮 `read` 少读首字符（路径 `/tmp/...` 变成 `tmp/...`），ffmpeg 报文件不存在，`set -e` 直接退出。`exec </dev/null` 救不了——它只改脚本自身 stdin，子进程继承的仍是 tsv |
| **波纹透明度加 90 下限托底** | `t = i/(N-1)` 归一化让末帧 t=1、alpha 归零，实测 ripple 在 t≥0.7s 后非透明像素直接为 0。叠加到 4c 末尾那次点击时波纹只显示 0.1s。改成 `t = i/N` + alpha 下限，0.8s 内非透明像素 280→1656全程可见 |
| **开场突出汉化重点（规模 + 专业度）** | hook1 原写"2112 条界面翻译"数字不准（源码实际 `tr()` 调用 474 处），修正为"474 处界面文本"并点出覆盖维度（菜单·对话框·按钮·提示）；新增"翻译得专业"卡，用量化术语证据区别于机翻——弛豫密度（非松弛密度）、冻结核近似（frozen core 标准术语）、保留快捷键名，这些规范都来自 zh_CN.qm 里的翻译注释；分屏对照图底部加覆盖清单行。VS 徽标原 88px 压在中文菜单条上（PIL text y 是左上角，主体 404–492 盖住菜单条 426–484），缩到 56px 落进两菜单条之间的 100px 空隙 |
| **全片旁白（edge-tts 女声 + 卡点对齐 + BGM ducking）** | 成片原只有合成 BGM、无人声。新增 `scripts/video/narration.py`：按成片 7 个画面子段（开场/痛点/转折/建模/计算/可视化/结尾）写中文解说词，调 edge-tts（`zh-CN-XiaoxiaoNeural`，实测语速 4.84 字/秒）分段生成 mp3，用 `adelay` 把每段**固定放到画面起点**（而非连续串联——串联会让旁白时间轴随每段实长漂移、越往后越错位），再 `amix` 成连续旁白轨。compose_bili.sh 最终拼接时若旁白轨存在，则 BGM 音量压到 0.30 给旁白让位、amix 混合。实测旁白段 RMS 90–115、纯 BGM 段（数据条/收尾留白）降到 34–42，人声清晰压过背景；总时长不变（90.4s） |

### 差距仍在的地方

**平均间隔 2.54s vs 对标 0.74–1.92s**，静态帧 85.9% 略高于对标上限 83%。本轮靠 4c 加长到 12 秒（多 4 秒真实操作画面）把画面变化从 25 次推到 35 次，间隔从 3.40s 压到 2.54s，首次进入合格区间上沿。剩余差距的根因仍是**有效画面基数不够** —— 全片 88.9s 里真正的 IQmol 操作画面只有段 4 的 27 秒。要继续提升，只能**再录更多操作片段**（比如打开文件、切换标签页、调色板），在现有素材上做花样收益已经递减。

## 三、逐项拆解

### 3.1 前3秒：三个对标都做了同一件事——先给结果，不给界面

抽帧看开场（左边是我们的，右边是对标）：

**A · UVR5（139万）**：纯黑底，霓虹青大字「最强伴奏、人声提取」→ 直接一句话说完价值，**全程没有出现过软件界面**。第2帧就出文字。

**B · 沉浸式翻译（72万）**：第20帧已经是手绘白板风格的插画（电脑+人物+公式涂鸦），配粗黑描边字幕「你需要一个翻译器吗」。用**插画**而不是界面开场。

**C · 分屏读顶刊（50万）**：前6秒是静态界面配一句问句「《Science》之类的顶刊编辑论文为什么只有几页？」——**它靠提问留人**，而不是靠画面。

**我们的**：0–3.96 秒完全静止的一帧英文菜单，然后 3.96 秒才有第一次变化。**前4秒在B站是致命的**——列表页默认划过率在这一档最高。

### 3.2 字幕样式：头部全是大字+描边，我们是小字+半透明底条

- A/B/C 三个都是**超大粗体字，带黑色描边或硬阴影**，压在画面上部 1/3，永远不遮挡操作区。
- 我们用的是下三分之一处的**半透明黑底条**，字号明显偏小。

实测字高：A 和 B 的关键字幕在 1080p 下约 60–80px。我们目前约 44px。在手机端（竖屏 400px 宽）这已经接近可读下限。

### 3.3 画面构成：头部的"录屏占比"远低于直觉

抽帧观察：

- **A · UVR5**：黑底 + 大字 + LOGO，**没有一帧真实录屏**。399秒视频全是动效字幕。139万播放。
- **C · 分屏读顶刊**：界面为主，但配了漫画式"问号"贴纸、绿色品牌色块、杂志封面素材。
- **B · 沉浸式翻译**：手绘插画 + 界面 + 红箭头标注，三种视觉混合。

**我们**：97.8% 是静止录屏。这是"看起来像 PPT"的根本原因。

### 3.4 封面：文档式排版 vs 大字压满

见 `build-video/out/benchmark_covers.png`（上到下：我们 / C / B / A）。

- 三个对标全部是**2–4个大词组压满画面**，字号占画面高度 30%+，底色是高饱和纯色或深色渐变。
- A 甚至把「UVR5」做成主视觉主体，软件名成为图形的一部分。
- 我们的小字排版像产品说明书，缩到 B站 信息流尺寸后完全不可读。

### 3.5 数据展示：头部用"功能清单"，我们用"工作量清单"

- A 的关键词是「最强伴奏、人声提取」→ 功能。
- B 是「谷歌年度精选最佳插件」「凭什么入选」→ 权威背书 + 疑问。
- 我们是「2112 条翻译 · 153 个模块 · 34 页手册」→ **这是我们的工作量，不是用户收益**。

这三组数字对懂 IQmol 的人有意义，对刷信息流的用户是零。头部视频的数字都是"你能得到什么"而不是"我们做了多少"。

### 3.6 结尾互动

- A：简介给网盘 + GitHub 两处，评论区讨论多（6365 条）。
- C：简介是完整操作步骤，直接把教程文字化。
- D（Zotero）：简介引导到课程和公众号，**形成长尾引流**。

我们的收尾卡是二维码 + 三连，属于标准做法，无明显短板。

## 四、诚实的结论

### 我们做对的

1. 交叉溶解替代硬切，亮度曲线连续（31→34→41→50→85），不刺眼。
2. 字体已换成 Noto Sans CJK SC，中文渲染正确。
3. 标题信息型 + 封面有中英对照，识别成本低。
4. 数据真实不夸大，`2112/153/34` 可核验。

### 三个必须改的硬伤

| 问题 | 现状 | 对标基准 | 差距 |
|---|---|---|---|
| **开场 4 秒无变化** | 首次变化 3.96s | 0.48–0.5s | 前4秒近乎空屏 |
| **画面变化密度** | 每 6.25s | 每 2.25s | 需提到约 33 次/75s |
| **静态帧占比** | 97.8% | 73–88% | 需降到约 85% |

### 一个认知纠正

我们一直在想"如何让静态录屏看起来更生动"，但对标 A 证明了**根本不需要录屏**也能拿 139万播放。动态标注层（Ken Burns + 高亮框）只是补丁，收益有限。真正对标的做法是：**用大字动效承担信息，用录屏只承担"证明它真的能用"**。

### 时长判断

头部同类都在 2:14–6:40，**没有一条 75 秒的作品**。75秒这个长度在B站属于"短视频区间"，但短视频池的推荐逻辑又是另一套（信息密度要求极高）。当前 75 秒作为"投B站的主片"偏短——建议后续加一条 3–4 分钟的完整教程（分P 或独立投稿），把 75 秒当作引流片。这个不急着改，先把 75 秒本身做扎实。

B站数据抓取（需先 `curl -c bili_cookie.txt https://www.bilibili.com/` 拿匿名 buvid3）：

```bash
# 搜索：order=click 直接按播放量排序
api.bilibili.com/x/web-interface/search/type?search_type=video&order=click&keyword=...
# 元数据（时长/播放/点赞/收藏/封面）
api.bilibili.com/x/web-interface/view?bvid=...
# 直链（先从 view 拿 cid）
api.bilibili.com/x/player/playurl?bvid=...&cid=...&qn=32&fnval=1
```

**踩过的坑**：`pic` 字段取完整值需要读 view 接口，直接截断字符串会得到 NoSuchKey；封面地址必须用 https；playurl 的 cid 不能填 1。
